1Qué llega de Kafka8 min

Qué estás mirandoKafka transporta bytes, no texto. Al exportar sus mensajes a un fichero, cada uno queda como un sobre con seis campos. Cinco son metadatos de Kafka (de qué partición viene, en qué posición, cuándo…). El sexto, value, es el evento de la web, y viene en Base64: un texto ilegible que codifica esos bytes.

Un sobre de Kafka: la primera línea de 000.json.

{ "key": "VUEwMDAwMDAwMDAwMDAwMA==",Base64 · el usuario "offset": 0,número · posición en la partición "partition": 0,número · partición de Kafka "timestamp": 1596240000000,número · milisegundos "topic": "clickstream",texto · nombre del topic "value": "eyJkZXZpY2UiOiJDaHJvbWUiLCJlY29tbWVyY2Ui…"Base64 · EL EVENTO }

2Paso 1 · Abrir el sobre8 min

Qué estás mirandoDeshacer el Base64 tiene dos movimientos: unbase64() recupera los bytes originales (tipo BINARY, todavía ilegibles) y cast(… AS STRING) los interpreta como texto. No hay nada que elegir aquí: con datos de Kafka siempre se hace, y siempre igual.
  1. SQL
    %sql
SELECT
  key AS encoded_key,
  unbase64(key) AS decoded_key,
  value AS encoded_value,
  unbase64(value) AS decoded_value
FROM kafka_events_bronze_raw
LIMIT 5;
    Deberías verdecoded_key y decoded_value de tipo BINARY: son los bytes, todavía no se leen. Es solo el paso intermedio.
  2. SQL
    %sql
SELECT
  key AS encoded_key,
  cast(unbase64(key) AS STRING) AS decoded_key,
  value AS encoded_value,
  cast(unbase64(value) AS STRING) AS decoded_value
FROM kafka_events_bronze_raw
LIMIT 5;
    Deberías verEl sobre abierto. Cada par muestra el antes y el después:
    encoded_keydecoded_keydecoded_value
    VUEwMDAwMDAwMDAwMDAwMA==UA00000000000000{"device":"Chrome","ecommerce":{"purchase_revenue_in_usd":850.5,…},"event_name":"finalize",…,"geo":{"city":"Madrid",…}

5Opción STRUCT: darle una forma fija12 min

Qué estás mirandoLe dices a Databricks exactamente qué forma tiene el JSON: qué campos, de qué tipo y cuáles son objetos o listas. A cambio, cada campo pasa a tener su tipo real (el importe es DOUBLE, items es una lista de verdad) y las consultas van más rápido. El esquema no hace falta escribirlo a mano: schema_of_json() lo deduce de un ejemplo.
  1. SQL
    %sql
SELECT schema_of_json('{"device":"Linux","ecommerce":{"purchase_revenue_in_usd":1881.0,"total_item_quantity":2,"unique_items":1},"event_name":"finalize","event_previous_timestamp":1596240138488000,"event_timestamp":1596240190421000,"geo":{"city":"Bilbao","state":"PV"},"items":[{"coupon":"NEWBED10","item_id":"M_STAN_Q","item_name":"Standard Queen Mattress","item_revenue_in_usd":1881.0,"price_in_usd":940.5,"quantity":2}],"traffic_source":"search","user_first_touch_timestamp":1595289600000000,"user_id":"UA00000000000011"}')
AS schema;
    Por qué estoSe aplica a una compra con todos los campos rellenos. Con una visita (items vacío) el esquema no sabría qué hay dentro de la lista, y con un campo a null no sabría su tipo.
    Deberías verUna fila con el esquema deducido. Léelo como el JSON de arriba: ecommerce: STRUCT<…>, geo: STRUCT<city, state> e items: ARRAY<STRUCT<coupon, item_id, …>>.
  2. SQL
    %sql
CREATE OR REPLACE TABLE kafka_events_bronze_struct AS
SELECT
  * EXCEPT (decoded_value),
  from_json(
    decoded_value,
    'STRUCT<device: STRING, ecommerce: STRUCT<purchase_revenue_in_usd: DOUBLE, total_item_quantity: BIGINT, unique_items: BIGINT>, event_name: STRING, event_previous_timestamp: BIGINT, event_timestamp: BIGINT, geo: STRUCT<city: STRING, state: STRING>, items: ARRAY<STRUCT<coupon: STRING, item_id: STRING, item_name: STRING, item_revenue_in_usd: DOUBLE, price_in_usd: DOUBLE, quantity: BIGINT>>, traffic_source: STRING, user_first_touch_timestamp: BIGINT, user_id: STRING>'
  ) AS value
FROM kafka_events_bronze_decoded;

SELECT *
FROM kafka_events_bronze_struct
LIMIT 10;
    Deberías verUna columna value de tipo STRUCT que puedes desplegar en la tabla de resultados. En texto plano, Databricks la representa así:
    decoded_keyvalue
    UA00000000000000List(Chrome, List(850.5, 1, 1), finalize, null, …, List(Madrid, MD), List(List(NEWBED10, M_STAN_T, …)), email, …)
    Ya no es texto: son campos con su tipo, uno dentro de otro.
  3. SQL
    %sql
SELECT
  decoded_key,
  value.device as device,
  value.geo.city as city,
  value.items as items,
  array_size(items) AS number_elements_in_array

6Opción VARIANT: forma flexible8 min

Qué estás mirandoVARIANT guarda el JSON en un formato binario que Databricks sabe recorrer rápido, sin que le des un esquema. No calculas ni pegas nada: parse_json y listo. Cuando consultas, : te devuelve otro VARIANT y tú decides el tipo con :: en el momento de usarlo.
  1. SQL
    %sql
CREATE OR REPLACE TABLE kafka_events_bronze_variant AS
SELECT
  decoded_key,
  offset,
  partition,
  timestamp,
  topic,
  parse_json(decoded_value) AS json_variant_value
FROM kafka_events_bronze_decoded;

SELECT *
FROM kafka_events_bronze_variant
LIMIT 5;
    Deberías verLa tabla kafka_events_bronze_variant con la columna json_variant_value de tipo VARIANT. Compárala con el paso 2 del bloque 5: aquí no hubo ningún esquema.
  2. SQL
    %sql
SELECT
  json_variant_value,
  json_variant_value:device :: STRING,
  json_variant_value:items
FROM kafka_events_bronze_variant
LIMIT 10;
    Deberías verAsí lo devolvió Databricks:
    deviceitems
    Chrome[{"coupon":"NEWBED10","item_id":"M_STAN_T",…}]
    Safari[{"coupon":null,"item_id":"M_PREM_T",…}]
    Se parece al bloque 4, pero no es lo mismo: items aquí es un VARIANT que conserva su estructura de lista, no una cadena.
    3. Si algo fallaSi parse_json da un error de tipo no soportado, tu entorno Serverless es la versión 1: cámbialo en el panel Environment. Si sigue sin funcionar, salta al bloque 7.

7La misma pregunta, tres formatos10 min

Qué estás mirandoAquí se ve la diferencia práctica. Primero, qué tipo tiene el importe de una compra en cada tabla. Después, una pregunta de negocio real, ¿cuánto se ha vendido en cada ciudad?, resuelta con los tres formatos.
  1. SQL
    %sql
SELECT 'STRING' AS formato,
       typeof(decoded_value:ecommerce.purchase_revenue_in_usd) AS tipo_del_importe
FROM (SELECT * FROM kafka_events_bronze_decoded LIMIT 1)
UNION ALL
SELECT 'STRUCT', typeof(value.ecommerce.purchase_revenue_in_usd)
FROM (SELECT * FROM kafka_events_bronze_struct LIMIT 1)
UNION ALL
SELECT 'VARIANT', typeof(json_variant_value:ecommerce.purchase_revenue_in_usd)
FROM (SELECT * FROM kafka_events_bronze_variant LIMIT 1);
    Deberías ver
    formatotipo_del_importe
    STRINGstring
    STRUCTdouble
    VARIANTvariant
    El mismo 850.5, tres tipos distintos.
  2. SQL
    %sql
-- STRING: hay que convertir el importe en cada consulta
SELECT decoded_value:geo.city AS ciudad,
       round(sum(decoded_value:ecommerce.purchase_revenue_in_usd::DOUBLE), 2) AS ingresos
FROM kafka_events_bronze_decoded
WHERE decoded_value:event_name = 'finalize'
GROUP BY ALL ORDER BY ingresos DESC;

-- STRUCT: los tipos ya están, se suma directamente
SELECT value.geo.city AS ciudad,
       round(sum(value.ecommerce.purchase_revenue_in_usd), 2) AS ingresos
FROM kafka_events_bronze_struct
WHERE value.event_name = 'finalize'
GROUP BY ALL ORDER BY ingresos DESC;

-- VARIANT: se convierte con :: al usarlo (y para agrupar, a STRING)
SELECT json_variant_value:geo.city::STRING AS ciudad,
       round(sum(json_variant_value:ecommerce.purchase_revenue_in_usd::DOUBLE), 2) AS ingresos
FROM kafka_events_bronze_variant
WHERE json_variant_value:event_name::STRING = 'finalize'
GROUP BY ALL ORDER BY ingresos DESC;
    Por qué estoEn VARIANT, la ciudad se convierte a STRING porque no se puede agrupar ni comparar un VARIANT directamente. Es el mismo precio que en STRING, pero con datos que ya están en binario y no hay que reinterpretar.
    Deberías verLas tres dan lo mismo: 6 ciudades con 50 compras cada una, de Valencia (96.709,90) a Madrid (81.715,30), 538.562,30 USD en total.
    3. Comprueba que lo has entendidoCon 2.252 eventos las tres van igual de rápido. Con 2.000 millones, la versión STRING reinterpretaría cada texto JSON en cada consulta. Por eso nadie analiza en STRING a escala: o le das forma (STRUCT) o lo guardas en un formato que se recorre rápido (VARIANT).

8El JSON cambia: por qué existe VARIANT8 min

Qué estás mirandoLos productores de eventos añaden campos sin avisar. 00_preparar_entorno dejó en events-kafka-extra/ dos ficheros más recientes en los que algunos eventos traen un campo nuevo, campaign, que no estaba cuando sacaste el esquema del bloque 5.
  1. SQL
    %sql
WITH eventos AS (
  SELECT cast(unbase64(value) AS STRING) AS decoded_value
  FROM read_files("/Volumes/lab0505/upload/upload/events-kafka-extra", format => "json")
)
SELECT
  count(*) AS eventos,
  count(decoded_value:campaign) AS con_campaign
FROM eventos;
    Deberías vereventos = 1.100 y con_campaign = 367.
  2. SQL
    %sql
WITH eventos AS (
  SELECT cast(unbase64(value) AS STRING) AS decoded_value
  FROM read_files("/Volumes/lab0505/upload/upload/events-kafka-extra", format => "json")
)
SELECT
  from_json(decoded_value, 'STRUCT<device: STRING, ecommerce: STRUCT<purchase_revenue_in_usd: DOUBLE, total_item_quantity: BIGINT, unique_items: BIGINT>, event_name: STRING, event_previous_timestamp: BIGINT, event_timestamp: BIGINT, geo: STRUCT<city: STRING, state: STRING>, items: ARRAY<STRUCT<coupon: STRING, item_id: STRING, item_name: STRING, item_revenue_in_usd: DOUBLE, price_in_usd: DOUBLE, quantity: BIGINT>>, traffic_source: STRING, user_first_touch_timestamp: BIGINT, user_id: STRING>') AS como_struct,
  parse_json(decoded_value):campaign AS campaign_en_variant
FROM eventos
WHERE decoded_value:campaign IS NOT NULL
LIMIT 5;
    Deberías verEn como_struct no aparece campaign: el esquema fijo lo ha descartado sin avisar. En campaign_en_variant está entero, por ejemplo {"channel":"social","experiment":"layout-b","id":"campaign-6"}.
Entonces, ¿cuál elijo? En un proyecto real no se elige uno para todo: cada capa usa el suyo.
KafkaBase64
→
BronzeVARIANT
Guardas el evento entero. Si mañana llega campaign, no lo pierdes.
→
SilverSTRUCT / columnas
Solo los campos que el negocio usa, con su tipo, y items explotado.
STRING queda para archivar el texto original o para consultas puntuales.
Si algo fallaSi el recuento da 0 eventos, la carpeta events-kafka-extra no existe: vuelve a ejecutar 00_preparar_entorno.
Fin del laboratorioSabes llevar un mensaje de Kafka desde el Base64 hasta columnas que se pueden sumar y explotar, y sobre todo sabes cuándo usar cada formato: VARIANT para guardarlo todo en Bronze aunque cambie, STRUCT o columnas tipadas para lo que el negocio consulta en Silver.
