One bad query, three symptoms

An online shop wants 2024 revenue per customer, tier and product category. The query joins four tables and it is slow. MThe method, before you measure3 min

What you are looking atEvery step of this lab follows the same loop. The temptation is to jump straight to a fix (rewrite the join, add a hint, buy a bigger cluster) on a hunch. A wrong hunch costs days and can make things worse. So you look first, change one thing, and prove it.
1 · MeasureQuery Profile and system.query.history
→
2 · Name itFind the bottleneck (Performance Insights names it for you, where available)
→
3 · One fixOne change per round, or you will not know which one helped
→
4 · BenchmarkMedian of several runs, result cache off, cost and time
Two clocksThe Query Profile shows two durations. Wall-clock is what the user waited. Aggregated task time is the sum of the time of every task on every core: the work the platform did, and on serverless what you pay for. Task time is never below wall-clock. Much bigger means many cores worked at once. Close to it means the work went through a few tasks while the other cores waited: not always a problem, but it is exactly how skew looks.
No profile for cache hitsIf the result cache answers a query, no work happens and the Query Profile is not available. To measure, make every run really execute: a unique comment in the SQL text (what the benchmark helper does), or SET use_cached_result = false on a SQL warehouse. In system.query.history, from_result_cache = true gives a cache hit away. The disk cache is different: it keeps running and only changes the time, never what is pruned.
Before you tuneCheck what the platform already did for you: Photon (tasks time in Photon), AQE (the final plan) and, on managed tables, Predictive Optimization. Tune only the part they did not cover.

1Measure first: three symptoms8 min

What you are looking atRun the bad query once and read its Query Profile. You are looking for three things, and each one has its own view of the graph: the details panel for pruning, the Memory peak colouring for the shuffle, and the Rows colouring for the skew.
  1. Python
    %python
QUERY_A = """
-- A · the bad query, as someone wrote it
SELECT c.customer_id, c.tier, p.category,
       SUM(oi.quantity * p.list_price) AS revenue,
       COUNT(*)                        AS line_items
FROM lab2402.shop.orders o
JOIN lab2402.shop.order_items oi ON o.order_idx = oi.order_idx
JOIN lab2402.shop.products p     ON oi.product_idx = p.product_idx
JOIN lab2402.shop.customers c    ON o.customer_idx = c.customer_idx
WHERE date_format(o.order_date, 'yyyy-MM') BETWEEN '2024-01' AND '2024-12'
GROUP BY c.customer_id, c.tier, p.category
ORDER BY revenue DESC
"""

display(spark.sql(QUERY_A))

    You should seeRevenue per customer, tier and category, highest first. The top rows belong to one "customer" of tier guest: the placeholder that holds every guest checkout.
  3. 📷 Screenshot to take: 2402-04-a-no-pruning.png
    You should seeFiles pruned 0, although the query only wants one year out of two. The filter wraps order_date in a function, and the dates are mixed in every file anyway.
  4. 📷 Screenshot to take: 2402-05-a-memory-peak-shuffle.png
    You should seeThe darkest nodes are Shuffle nodes, and they lead the list with the most memory. The dimensions are too big to broadcast, so each of the three joins moves both sides across the network: tens of millions of rows of order_items travel before any aggregation.
  5. 📷 Screenshot to take: 2402-06-a-rows-skew.png

    6. If something failsIf the Rows colouring does not make the hot path obvious, compare the two clocks in the details panel and the duration of the tasks of the stage: one task much longer than the median (5 times or more) is the skew.

What you are looking atYou have the symptoms. Now let the tool name them. In a workspace with Performance Insights (a preview a workspace admin enables), the top of the Query Profile has an Optimize button. It hands the query, its profile and its insights to Genie Code, which reads them and answers with a recommendation in two instructions. Free Edition does not have it, so this block shows what the answer looks like for query A. You do not need to read every metric yourself: the tool reads them for you, you check its claim with a benchmark.
  1. Watch outScreenshot taken in a workspace with Performance Insights enabled. Not available in Free Edition.
    📷 Screenshot to take: 2402-07-genie-optimize.png
    2. Genie Code recommendationReplace date_format(order_date, 'yyyy-MM') BETWEEN … with a direct date range on order_date, then cluster the table on order_date to enable file pruning.
    4. Why two instructions?Instruction 1 removes the function, so the engine can use the per-file min/max. Instruction 2 reorders the data, so the files are organized by date. Without both, Files pruned stays at 0. This lab proves it: you apply them one at a time and benchmark each one.
    And the shuffle and the skew?Performance Insights also flags them (data skew, the shuffle-heavy joins), but the recommendation starts with reading: every row you do not read is a row that does not travel in the shuffle nor pile up in the hot partition. Watch the Memory peak and the Rows of query C: the same joins, much less data.

2Benchmark A, honestly4 min

What you are looking atOne run proves nothing: on serverless, compute varies from run to run. An honest benchmark has four rules: bypass the result cache (a unique comment per run), discard a warm-up run, keep the median of several runs, and change one thing at a time. A is benchmarked now, on the layout it was written for.

3Instruction 1: fix the predicate5 min

What you are looking atOne change only: the filter on the raw order_date. The table is still unclustered.
  1. Python
    %python
QUERY_B = """
-- B · instruction 1: the filter on the raw column, nothing else changes
SELECT c.customer_id, c.tier, p.category,
       SUM(oi.quantity * p.list_price) AS revenue,
       COUNT(*)                        AS line_items
FROM lab2402.shop.orders o
JOIN lab2402.shop.order_items oi ON o.order_idx = oi.order_idx
JOIN lab2402.shop.products p     ON oi.product_idx = p.product_idx
JOIN lab2402.shop.customers c    ON o.customer_idx = c.customer_idx
WHERE o.order_date >= DATE'2024-01-01' AND o.order_date < DATE'2025-01-01'
GROUP BY c.customer_id, c.tier, p.category
ORDER BY revenue DESC
"""

display(spark.sql(QUERY_B))
    📷 Screenshot to take: 2402-09-b-still-no-pruning.png
    You should seeFiles pruned is still 0. The engine can now use the min/max of every file, but every file spans both years, so no file can be skipped. That is the "why two instructions" of Genie Code, measured.
  2. Python
    %python
benchmark("B", QUERY_B)
    📷 Screenshot to take: 2402-10-benchmark-b.png
    You should seeA median close to A's. One instruction alone does not change what is read.

4Instruction 2: fix the data layout6 min

What you are looking atNow the layout: orders clustered by date, with a smaller target file size so a one-year filter can skip whole files. OPTIMIZE … FULL reclusters the existing data, not only new files. The query does not change: you run B again, and its benchmark is labelled C.
  1. Python
    %python
spark.sql(f"ALTER TABLE lab2402.shop.orders SET TBLPROPERTIES ('delta.targetFileSize' = '{LAYOUT_FILE_SIZE}')")
spark.sql("ALTER TABLE lab2402.shop.orders CLUSTER BY (order_date)")
spark.sql("OPTIMIZE lab2402.shop.orders FULL")      # recluster the existing data, not only new files

End of the labOne bad query, three symptoms. No pruning came from the filter and the layout, and it took Genie Code's two instructions together to fix it: the raw-column filter alone pruned nothing. The heavy shuffle and the skew came from the joins and the data: three shuffle joins over tens of millions of rows, and one guest "customer" holding a quarter of the orders. Reading less made them smaller, not different. And every claim came with an honest benchmark: cache bypassed, warm-up discarded, median, one change at a time.
